# 3. 管理行动方案

## 决策结论

六月并不是全站商品需求出现了问题，而是把三个本就有风险的选择叠加进了同一场活动：

1. 付费社交投放增长过快，渠道贡献利润转负。
2. `SUMMER20` 继续压低了活动订单在营销成本前的利润率。
3. TrailFlex Runner 19.8% 的退货率进一步放大退款和处理成本。

## 七月行动

- 暂停扩大付费社交，直到按获客批次计算的渠道贡献利润重新转正。
- 用按品类设置的优惠替代全场八折，并排除低利润商品。
- 从拉新广告中撤下 TrailFlex Runner，修正尺码指引并每周监控退货率。
- 继续投入自然搜索和邮件：它们不依赖深折扣也能产生正贡献。

## 让 Agent 复核并更新 Canvas

在 **设置 → AI** 配置模型，打开 [[zh/经营复盘.stela.canvas|经营复盘 Canvas]] 和 Agent 面板，然后运行下面的任务：

> 使用 `ecommerce-unit-economics` Skill 和 `local-mysql`，验证为什么六月订单与净收入增长，贡献利润率却大幅下降。重新执行必要 SQL，对比渠道、促销和 SKU 证据，然后更新当前已经打开的经营复盘 Canvas，补充简洁的管理结论和从证据到行动的流程。不要新建第二个 Canvas。

这会产生一次真实的 Agent 运行；成功的 `run_sql` 结果会成为 Canvas 的最新可审计数据源。

## 检查真实运行

Agent 完成后，从底部栏打开 **Agent Dashboard**，检查：

- 本次 Agent 的完成状态与耗时；
- `run_sql`、`load_skill` 和 Canvas 工具活动；
- 实际加载的 `ecommerce-unit-economics` Skill；
- Token 使用和脱敏 Trace。

在你真正运行 Agent 之前，Dashboard 保持空白；Demo 不会伪造可观测性数据。

## 下周直接复用

新建一篇使用 `local-mysql` 的笔记，加入 RunSQL 块，并在块内按 **Mod+Shift+P**。插入：

- **Channel contribution / 渠道贡献利润**，复用任意周期的渠道复盘；
- **High-return SKU / 高退货商品**，按品类或更高销量门槛检查退货风险。

相同的 `{{变量}}` 会联动编辑，因此日期或渠道只需修改一次。返回 [[README|Demo 首页]]。
